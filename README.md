# Docker Log Parser

Real-time Docker container log viewer with SQL query analysis and GraphQL request management.

## Quick Start

```bash
# Build frontend (TypeScript + Vue)
cd web
npm install
npm run build
cd ..

# Build backend (Go)
./build.sh

# Or build individually
go build -o docker-log-viewer cmd/viewer/main.go

# Run viewer
./docker-log-viewer
```

Open [http://localhost:9000](http://localhost:9000)

## Docker

### Using Docker Compose (Recommended for Development)

```bash
# Start the application with hot reload
docker-compose up

# Build and start in detached mode
docker-compose up -d --build

# View logs
docker-compose logs -f

# Stop the application
docker-compose down
```

The Docker Compose setup:
- Builds frontend automatically on startup
- Enables hot reload with Air for Go backend
- Mounts source code for development
- Exposes port 9000
- Connects to Docker socket for log monitoring

### Using Docker (Production)

```bash
# Build production image
docker build -t docker-log-viewer .

# Run container
docker run -d \
  -p 9000:9000 \
  -v /var/run/docker.sock:/var/run/docker.sock \
  --name docker-log-viewer \
  docker-log-viewer

# With PostgreSQL connection
docker run -d \
  -p 9000:9000 \
  -v /var/run/docker.sock:/var/run/docker.sock \
  -e DATABASE_URL="postgresql://user:pass@host:5432/db" \
  --name docker-log-viewer \
  docker-log-viewer
```

## Features

- **Real-time streaming** - Monitor all Docker containers simultaneously
- **EKS pod logs** - Stream Kubernetes pod logs from AWS EKS clusters alongside Docker (see [EKS Kubernetes Logs](#eks-kubernetes-logs))
- **Smart parsing** - Structured logs (key=value), JSON, timestamps, log levels
- **Interactive filtering** - Container selection, log level, live search, trace filtering
- **SQL analysis** - Query statistics, N+1 detection, slowest queries
- **EXPLAIN plans** - PostgreSQL execution plan visualization with PEV2 (requires DB connection)
- **Request Management** - Save, execute, and analyze GraphQL/API requests
- **Before/After Analysis** - Track request performance over time
- **TypeScript + Vue 3** - Modern, type-safe frontend with reactive UI

Save and execute GraphQL/API requests with full log capture and SQL analysis.

**Web UI**: [http://localhost:9000/requests.html](http://localhost:9000/requests.html)

Server setup, sample queries, and execution dialogs accept **Custom Headers** as a JSON object of string values:

```json
{"X-GlueDev-UserID": "user-id", "X-Glue-Experimental-Mode": "enabled"}
```

Headers inherit from the server, then the sample query, then execution overrides (case-insensitive). An empty object inherits defaults; an empty string value overrides a header with an empty value. Custom `Authorization` overrides the bearer token. `X-Request-Id` and transport headers such as `Host` and `Content-Length` are managed automatically and cannot be overridden. Existing User ID and experiment settings remain compatible and appear as custom headers when editing a server.

Headers are stored in the local database, including execution snapshots for replay; treat database files as sensitive if headers contain credentials. The additive database migration runs on startup.

**CLI**:
```bash
# Save a request
./graphql-tester -url "https://api.example.com/graphql" \
                 -data graphql-operations-unique/AuthConfig.json

# Execute immediately
./graphql-tester -url "https://api.example.com/graphql" \
                 -data operations/query.json \
                 -execute

# List saved requests
./graphql-tester -list
```



### Comparison Tool

Compare API endpoints by analyzing logs and SQL performance.

```bash
go build -o compare cmd/compare/main.go
./compare -url1 <url1> -url2 <url2> -data request.json
```

Generates HTML report with SQL statistics and performance comparison.

### Query Analysis Tool

Compare SQL queries from two saved execution IDs.

```bash
go build -o analyze cmd/analyze/main.go
./analyze -exec1 1 -exec2 2

# Save to file
./analyze -exec1 1 -exec2 2 -output report.txt

# Verbose mode with all queries
./analyze -exec1 1 -exec2 2 -verbose
```

Analyzes query performance, identifies regressions, and provides index recommendations.
See [cmd/analyze/README.md](cmd/analyze/README.md) for full documentation.

## EKS Kubernetes Logs

Pod logs from EKS clusters flow through the same pipeline as Docker logs: same parser,
filters, trace IDs, and SQL analysis. Each pod container shows up on the Logs page grouped
under `eks:<cluster>` and named `<namespace>/<pod>/<container>`.

### Setup

1. **Sign in to AWS** with any method the AWS CLI supports. The viewer uses the standard
   credential chain (env vars, `~/.aws/config` profiles, SSO cache, instance roles):

   ```bash
   aws configure sso --profile dev      # one-time SSO profile setup
   aws sso login --profile dev          # or use "SSO Login" in Settings
   # or: export AWS_ACCESS_KEY_ID=... AWS_SECRET_ACCESS_KEY=... AWS_SESSION_TOKEN=...
   ```

2. **Add a cluster** in **Settings → EKS Clusters → + Add EKS Cluster**:
   - **AWS Profile** – profile from `~/.aws/config` (empty = default chain / env vars)
   - **Region** – e.g. `us-east-1`; click **Discover Clusters** to list clusters and verify credentials
   - **Namespace** – limit to one namespace (empty = all)
   - **Label Selector** – standard Kubernetes selector, e.g. `app=api,tier!=batch`
   - **Initial history** – minutes of logs to load when a stream starts (like `kubectl logs --since`)

   Example configuration (`POST /api/eks/clusters`):

   ```json
   {
     "name": "staging",
     "region": "us-east-1",
     "profile": "dev",
     "namespace": "api",
     "labelSelector": "app.kubernetes.io/name=api",
     "sinceMinutes": 15,
     "enabled": true
   }
   ```

Running pods are re-discovered every 5 seconds; each running container is followed like
`kubectl logs -f --timestamps`. If credentials expire, the cluster shows an error in Settings
and reconnects automatically after you sign in again.

Credentials are never stored by the viewer: AWS SDK credentials are cached in memory, and
EKS bearer tokens (presigned STS `GetCallerIdentity`, equivalent to `aws eks get-token`) are
generated in-process and refreshed every 14 minutes.

### Docker Compose

`docker-compose.yml` mounts `~/.aws` into the container. Run `aws sso login` on the host; the
container picks up the shared SSO token cache. (The "SSO Login" button needs the AWS CLI on
the machine running the viewer.)

### Required permissions

IAM policy for the identity used by the viewer:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["eks:ListClusters", "eks:DescribeCluster"],
      "Resource": "*"
    }
  ]
}
```

`sts:GetCallerIdentity` needs no permission. The identity must also be authorized **inside**
the cluster to read pods and logs, via an EKS access entry or the `aws-auth` ConfigMap,
bound to a role like:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: log-viewer
rules:
  - apiGroups: [""]
    resources: ["pods", "pods/log"]
    verbs: ["get", "list"]
```

With access entries, the managed `AmazonEKSViewPolicy` covers this.

### API

| Method | Path | Purpose |
|--------|------|---------|
| GET | `/api/eks/clusters` | Saved clusters + live connection status |
| POST / PUT / DELETE | `/api/eks/clusters[/{id}]` | Manage clusters |
| GET | `/api/eks/discover?profile=&region=` | Verify credentials, list clusters |
| POST | `/api/eks/login` | Start `aws sso login` for `{"profile": "..."}` |
